# תהליך העבודה — BMAD ו-Skills בפרויקט

> מסמך זה מסביר מה זה BMAD, אילו "סקילים" (יכולות מוכנות מראש) יש לנו, ובאיזה סדר נשתמש בהם בפרויקט הזה. המטרה: שכל מי שיצטרף לפרויקט — גם מי שלא מכיר את Claude Code או BMAD — יבין איך אנחנו עובדים ולמה, בלי לנחש.

---

## מה זה BMAD, בקצרה

BMAD הוא **מתודולוגיית עבודה** (לא ספריית קוד) שמחלקת פרויקט תוכנה לשלבים ברורים, כשלכל שלב יש "סוכן" (Agent) עם תפקיד מוגדר — בדיוק כמו צוות אנושי אמיתי (אנליסט, מנהל מוצר, מעצב UX, אדריכל מערכת, מפתח). כל שלב מייצר **מסמך** שנשמר בפרויקט, כך שההחלטות לא "נעלמות" בשיחה — הן נשארות כתובות וניתנות למעקב.

זו הסיבה ש-BMAD מתאים בול לבקשה שלכן ל"סדר, הקפדה על רישום מדויק, ותיעוד כל החלטה" — זו בדיוק הפילוסופיה שלו.

**איפה זה נשמר בפרויקט הזה** (מוגדר ב-`_bmad/config.toml`):
- `_bmad-output/planning-artifacts/` — מסמכי תכנון (PRD, ארכיטקטורה, UX spec).
- `_bmad-output/implementation-artifacts/` — סטורי-פיילים, תיעוד ספרינטים.
- `docs/` — "ידע פרויקט" קבוע (כמו המסמך הזה, ויומן ההחלטות הטכנולוגיות).
- שפת הפלט מוגדרת כבר ל**עברית**.

## הסדר המומלץ לפרויקט הזה

```
1. (אופציונלי) Analyst — גיבוש/אימות דרישות נוספות
2. PM → יוצר PRD רשמי מתוך שני המסמכים שסופקו
3. UX Designer → מפרט מסכים וזרימות למסך אנשי קשר + טופס רישום ציבורי
4. Architect → מכריע על כל ההחלטות הטכניות הפתוחות, מתעד ב-Architecture doc
5. שער איכות: "בדיקת מוכנות ליישום" — ולידציה שה-PRD/UX/Architecture שלמים ועקביים
6. פירוק ל-Epics + Stories → יחידות עבודה קטנות וברורות
7. לכל Story: Dev (עם בדיקות יחידה) → Code Review → (בהמשך) בדיקות E2E
8. מעקב שוטף: סטטוס ספרינט, ולבסוף רטרוספקטיבה
```

זה בדיוק העיקרון של "לשאול לפני כל פעולה" שביקשתן — בכל מעבר בין שלבים, אני **אציג** את התוצר ואבקש אישור/הערות לפני שממשיכים לשלב הבא.

## טבלת כל ה-Skills המותקנים, מקובצים לפי מטרה

### א. תכנון (Planning) — משתמשים בהם פעם אחת/כמה פעמים בתחילת הפרויקט

| Skill | מה הוא עושה | רלוונטי כאן? |
|---|---|---|
| `bmad-product-brief` | בונה "תמצית מוצר" קצרה — שכבה קלה לפני PRD מלא | אופציונלי — יש לנו כבר מסמך דרישות עשיר, אפשר לדלג |
| `bmad-prd` | יוצר/מעדכן/מוודא PRD מלא | **כן, השלב הראשון בפועל** |
| `bmad-ux` | תכנון UX ומסכים | **כן** |
| `bmad-architecture` | בונה "עמוד שדרה" ארכיטקטוני — כל ההחלטות הטכניות + הנימוקים | **כן** |
| `bmad-check-implementation-readiness` | בודק שה-PRD/UX/Architecture/Epics שלמים לפני שמתחילים לקודד | **כן — שער איכות חשוב לפני קוד ראשון** |

### ב. פירוק עבודה (Breakdown)

| Skill | מה הוא עושה |
|---|---|
| `bmad-create-epics-and-stories` | פירוק ה-PRD ל"אפוסים" (יחידות עבודה גדולות) ו"סטוריז" (משימות קטנות וברורות) |
| `bmad-create-story` | יוצר קובץ סטורי בודד עם כל ההקשר הדרוש למפתח (כולל AC — קריטריוני קבלה) |
| `bmad-sprint-planning` | ממיר את רשימת ה-Epics/Stories למעקב ספרינטים |

### ג. פיתוח וביצוע (Execution)

| Skill | מה הוא עושה |
|---|---|
| `bmad-dev-story` | מיישם סטורי בודד לפי TDD — קודם כותב טסט שנכשל, אז קוד שעובר אותו, אז מנקה (Red-Green-Refactor) |
| `bmad-quick-dev` | גרסה קלה יותר ליישום שינוי/תיקון קטן שלא מצדיק סטורי מלא |
| `bmad-qa-generate-e2e-tests` | מייצר בדיקות End-to-End (בודקות את המערכת כמו משתמש אמיתי בדפדפן) לפיצ'ר קיים |

### ד. איכות ובקרה (Quality Gates)

| Skill | מה הוא עושה |
|---|---|
| `bmad-code-review` | בודק קוד שנכתב בצורה "עוינת" בכוונה (Blind Hunter / Edge Case Hunter / Acceptance Auditor) — מוצא באגים לפני שהם מגיעים לפרודקשן |
| `bmad-review-edge-case-hunter` | מתמקד במקרי קצה שלא טופלו |
| `bmad-review-adversarial-general` | ביקורת ביקורתית כללית על כל תוצר (לא רק קוד) |
| **`bmad-checkpoint-preview`** | **עצירה ל"סקירה אנושית" — בדיוק המנגנון שיאפשר לכן לבדוק כל שינוי לפני שממשיכים** |

### ה. תיעוד וניהול פרויקט (Docs & Project Management)

| Skill | מה הוא עושה |
|---|---|
| `bmad-index-docs` | בונה/מעדכן אינדקס לכל הקבצים בתיקיית `docs/` — כדי שקל יהיה למצוא כל מסמך |
| `bmad-generate-project-context` | יוצר קובץ הנחיות בסיסי ל-AI (כללי הפרויקט, מוסכמות) |
| `bmad-document-project` | מתעד פרויקט קיים (Brownfield) — לא רלוונטי כרגע כי מתחילים מאפס |
| `bmad-shard-doc` | מפצל מסמך ארוך (כמו PRD שגדל) לכמה קבצים קטנים וברורים |
| `bmad-sprint-status` | תמונת מצב של הספרינט הנוכחי |
| `bmad-retrospective` | לקחים בסוף כל Epic |
| `bmad-correct-course` | תהליך מסודר לטפל בשינוי כיוון באמצע עבודה, בלי "לשבור" את התיעוד הקיים |
| `bmad-customize` | מתאים סוכן/סקיל ספציפי להעדפות שלכן (למשל: לשנות את סגנון השאלות של Amelia) |
| `bmad-help` | "מה לעשות עכשיו?" — נותן המלצה על הצעד הבא לפי מצב הפרויקט |

### ו. יצירתיות/מחקר (פחות רלוונטי כרגע, ל-MVP עם דרישות ברורות)

`bmad-brainstorming`, `bmad-domain-research`, `bmad-market-research`, `bmad-technical-research`, `bmad-forge-idea`, `bmad-prfaq`, `bmad-party-mode`, `bmad-advanced-elicitation` — כלים לשלב גיבוש רעיון/מחקר מקדים. שימושיים בעיקר **אם** יעלה צורך לחקור טכנולוגיה ספציפית (למשל: "מה השיטה הכי טובה לסנכרן עם מרכבה?") — אז נשתמש ב-`bmad-technical-research` נקודתית.

## מעבר ל-BMAD: כלי פיתוח "רגילים" שמומלץ להתקין (לא סקילים של BMAD, אלא תשתית קוד)

אלה לא "Skills" של Claude Code אלא **חבילות npm / כלים** סטנדרטיים בעולם Node/React. מפרט כל אחד כי ביקשתן הסבר לכל בחירה:

| כלי | מה הוא | למה מומלץ |
|---|---|---|
| **ESLint** | סורק את הקוד ומזהיר על טעויות נפוצות/סגנון לא עקבי, לפני שהקוד בכלל רץ | תקן-זהב בעולם JS/TS; Next.js מגיע איתו כברירת מחדל |
| **Prettier** | מסדר אוטומטית רווחים/פסיקים/מרכאות בקוד לפורמט אחיד | חוסך "ויכוחי סגנון" בין מפתחים; משתלב עם ESLint |
| **Husky + lint-staged** | מריצים ESLint/Prettier/טסטים **אוטומטית** לפני כל `git commit` | מונע "לדחוף" קוד שבור בטעות |
| **React Testing Library** | ספריית עזר לבדיקת קומפוננטות React (בודקת "מה המשתמש רואה", לא פרטי מימוש) | השלמה טבעית ל-Jest/Vitest לבדיקת ה-UI |
| **swagger-jsdoc + swagger-ui-react** (או `next-swagger-doc`) | מייצר תיעוד API אוטומטי מתוך הערות בקוד, ומציג אותו כעמוד אינטראקטיבי | **כבר הוחלט** — זו הבחירה שאישרתן |
| **Docker (אופציונלי)** | "קופסה" מבודדת שמריצה גרסת Postgres זהה אצל כולם, בלי להתקין Postgres ישירות על המחשב | נוח מאוד לסביבת פיתוח מקומית עקבית; לא חובה אם מעדיפות להתקין Postgres ישירות |
| **GitHub Actions** | מריץ אוטומטית lint + טסטים + build בכל push ל-GitHub | "רשת ביטחון" — רואים מיד אם commit שבר משהו |
| **dotenv (`.env`)** | קובץ מקומי (לא נכנס ל-git) לשמירת סודות כמו סיסמת מסד הנתונים | מונע דליפת סודות להיסטוריית git |

*כל הכלים בטבלה הזו — פרט ל-Swagger שכבר הוחלט — ייכנסו רשמית לרשימת ה"פתוח להחלטה" ביומן ההחלטות הטכנולוגיות, ונאשר אותם יחד בשלב הארכיטקטורה.*
