## 1. מבנה הפרויקט: Monorepo

**מה זה:** "מונוריפו" (Monorepo) הוא מבנה שבו כמה חלקים של המערכת (למשל: אתר, שרת, ספרייה משותפת) יושבים ב־repository (מאגר git) אחד, במקום ב־repo נפרד לכל חלק ("Polyrepo"). זה שונה מהמצב הנפוץ בפרויקטים קטנים, שבו יש repo אחד לכל אתר/שרת בנפרד.

**למה בחרנו בזה:** ביקשתם Monorepo — וזו בחירה טובה לפרויקט שצפוי לגדול (לפי מסמך הדרישות יש כבר 4 שלבי פיתוח מתוכננים, ואולי בעתיד גם כמה "אתרים" נפרדים — פנימי לרכזים, טופס ציבורי, אזור אישי לנתמכים).

**יתרונות:**
- קוד משותף (למשל: הגדרות טיפוסים, חיבור למסד הנתונים, קומפוננטות UI) נכתב פעם אחת ומיובא בכל מקום — בלי להעתיק-הדבק בין repos.
- שינוי אחד (למשל שינוי בסכמת מסד הנתונים) מתבצע ב-commit אחד שרואים בו את כל ההשפעה, במקום לתאם בין כמה repos.
- קל יותר לאכוף סטנדרטים אחידים (linting, טסטים, גרסאות חבילות) על כל הפרויקט.

**חסרונות / סיכונים:**
- ה־repo גדל עם הזמן וכלים "רגילים" (כמו `npm install` רגיל בלי הגדרה נכונה) יכולים להיות איטיים אם לא מגדירים נכון.
- דורש כלי ניהול ייעודי (ראו Turborepo למטה) כדי שהבנייה (build) והרצת הטסטים לא יריצו מחדש דברים שלא השתנו.

**חלופות שנשקלו:** Polyrepo (repo נפרד לכל אפליקציה) — פשוט יותר להתחיל בו, אבל לא מתאים כשיש קוד משותף בין חלקים, ודורש תיאום גרסאות ידני.

## 2. Turborepo — כלי ניהול ה-Monorepo

**מה זה:** Turborepo הוא כלי (נבנה ע"י Vercel, אותה חברה שעומדת מאחורי Next.js) שיודע להריץ פקודות (build, test, lint) על כל החלקים ב-monorepo בצורה חכמה: **קאשינג** — אם חלק מסוים לא השתנה, הוא לא בונה/בודק אותו שוב; **מקביליות** — מריץ משימות בלתי-תלויות זו בזו, ולא אחת אחרי השנייה.

**למה בחרנו בזה:** ביקשתם Turborepo — התאמה טבעית ל-Next.js (מאותה חברה), תיעוד טוב, ותצורה פשוטה יחסית (קובץ `turbo.json` אחד).

**יתרונות:**
- מהירות: בזכות הקאשינג, פקודות חוזרות (כמו הרצת טסטים אחרי שינוי קטן) מהירות משמעותית.
- קונפיגורציה מינימלית ביחס לחלופות.
- אינטגרציה מובנית עם Vercel (שירות האחסון שנפוץ להרצת אפליקציות Next.js) לקאשינג בענן, אם וכאשר נרצה.

**חסרונות / סיכונים:**
- כלי נוסף ללמוד (קובץ `turbo.json`, פקודות `turbo run ...`).
- פחות "עשיר" בפיצ'רים מתקדמים (כמו generators אוטומטיים) לעומת המתחרה המרכזית שלו, Nx.

**חלופות שנשקלו:** Nx (חזק יותר אך גם מורכב יותר להתחלה), npm workspaces "גולמי" בלי כלי ניהול (הכי פשוט אך בלי קאשינג/מקביליות — לא מתאים כשהפרויקט גדל).

## 3. npm כמנהל החבילות (ולא pnpm)

**מה זה "מנהל חבילות" (Package Manager):** הכלי שמוריד ומנהל את הספריות החיצוניות שהפרויקט תלוי בהן (כמו React, Next.js וכו') — לפי קובץ `package.json`. npm הוא מנהל החבילות שמגיע **מובנה** עם Node.js.

**למה בחרנו בזה:** ביקשתם npm במפורש (ולא pnpm).

**יתרונות:**
- מגיע מובנה עם כל התקנת Node.js — אין צורך להתקין כלי נוסף.
- הכי נפוץ ומוכר; כל מדריך/דוגמת קוד באינטרנט כתובה קודם כל בשבילו.
- מגרסה 7 ואילך תומך "workspaces" (ניהול כמה חבילות בפרויקט אחד) — מספיק בשביל ה-Monorepo שלנו.

**חסרונות / סיכונים (לשקיפות מלאה, גם אם ההחלטה כבר התקבלה):**
- **מהירות התקנה:** pnpm בדרך כלל מהיר יותר משמעותית בהתקנות חוזרות, כי הוא שומר את החבילות פעם אחת בדיסק ויוצר קישורים אליהן (במקום להעתיק בכל תיקייה).
- **גודל דיסק:** ב-monorepo עם כמה "אפליקציות" ש**חולקות** אותן ספריות, npm יכפיל את הספריות בכל תיקיית `node_modules`, בעוד pnpm חוסך מקום.
- **"תלויות רפאים" (Phantom Dependencies):** pnpm נוקשה יותר ומונע מצב שבו קוד "בטעות" מצליח לייבא חבילה שלא הוגדרה לו רשמית כתלות — npm מאפשר את זה, מה שיכול ליצור תקלות שקשה לאתר בעתיד.

מכיוון שזו החלטה מפורשת שלכם, נעבוד עם npm workspaces + Turborepo (שילוב נתמך היטב ותקין), רק חשוב שתדעו את ה-trade-off אם בהמשך יורגש כבד.

**חלופות שנשקלו:** pnpm (המומלץ הכי נפוץ למונוריפו כיום), yarn (workspaces גם קיים, פחות פופולרי כיום מ-pnpm).

## 4. Next.js — מסגרת העבודה המרכזית (Full-Stack, לא רק "שרת")

**מה זה:** Next.js היא מסגרת עבודה (framework) שבנויה **מעל** React. חשוב להבהיר נקודה שעלולה לבלבל: Next.js היא לא "שרת" בלבד — היא **גם** בונה את מסך המשתמש (מה שהמשתמש רואה בדפדפן, מבוסס React) **וגם** מספקת את השכבה השרתית (API Routes / Server Actions שמדברים עם מסד הנתונים). לכן React Hook Form, Mantine ו-Redux Toolkit (שסימנתם כ"קלינט") למעשה **רצים בתוך** אותה אפליקציית Next.js יחד עם pg/Prisma/Joi (שסימנתם כ"שרת") — לא בהכרח שני פרויקטים נפרדים.

**למה זה נבחר:** ציינתם את זה כבחירה קיימת. זו בחירה סבירה ונפוצה מאוד היום לאפליקציות עסקיות בעברית/RTL, עם קהילה ענקית.

**יתרונות:**
- שילוב client+server באותה מסגרת מפחית "חיכוך" (אין צורך בפרויקט שרת נפרד + פרויקט קליינט נפרד + CORS וכו').
- תמיכה מובנית ב-Server-Side Rendering — טוב ל-SEO ולביצועים ראשוניים (פחות קריטי כאן כי זו מערכת פנים-ארגונית, אבל לא מזיק).
- אקוסיסטם ענק, תיעוד מעולה, נתמך ע"י Vercel.

**חסרונות / סיכונים:**
- "יותר מדי אפשרויות" — Next.js מציעה כמה דרכים לעשות אותו דבר (Pages Router מול App Router, API Routes מול Server Actions), מה שעלול לבלבל מי שחדש בעולם. **נצטרך להחליט ולתעד איזו גישה נלך בה** בשלב הארכיטקטורה (Winston, אדריכל המערכת ב-BMAD, יציג את זה עם כל היתרונות/חסרונות).

**חלופות שנשקלו:** לא נדון בזה כי הבחירה כבר ניתנה; לצורך ההשוואה בלבד — Express.js לשרת נפרד + Vite/CRA לקליינט נפרד הן החלופה ה"קלאסית" שדורשת יותר תשתית משלימה (CORS, שני deployments נפרדים וכו').

**עדכון (24/09/2026, החלטת ר"צ + שלב ארכיטקטורה):** ה"חיסרון" שצוין למעלה (App Router מול Pages Router, API Routes מול Server Actions) **לא זה מה שהוכרע בסוף** — הוכרעה שאלה עמוקה יותר, שהמסמך הזה עצמו סימן כ"נדחה כי הבחירה כבר ניתנה": **הפרויקט עבר לארכיטקטורת קליינט/שרת מופרדת.** `Next.js` נשאר, אבל **רק** בתור ה-frontend (`apps/web`) — בלי API Routes, בלי גישה ישירה למסד הנתונים. כל ה-API + הלוגיקה העסקית עברו לאפליקציית שרת נפרדת לגמרי, ב-**NestJS** (`apps/api` — ר' סעיף חדש למטה). זו למעשה גרסה של החלופה ה"קלאסית" שתוארה כאן למעלה — רק עם NestJS במקום Express גולמי. הפירוט המלא (כולל ה-trade-offs: deployment כפול, קריאת רשת נוספת, CORS) ב-`ARCHITECTURE-SPINE.md` (AD-1, AD-12) וב-`expertise-api-rest`/`expertise-react-nextjs`. השאלה הפתוחה שסומנה בתחתית מסמך זה ("מבנה מדויק של האפליקציות") — **הוכרעה בכך**, ר' עדכון בסעיף המתאים.

## 4A. NestJS — מסגרת עבודה לשרת (`apps/api`) — הוחלט 24/09/2026

**מה זה:** NestJS היא framework לבניית שרתי Node.js, בנויה בהשראת Angular — מאורגנת סביב מודולים/controllers/services עם Dependency Injection מובנה. שונה מ-Express (שהיה "חלופה קלאסית" שצוינה בסעיף 4 למעלה) בכך שהיא מגיעה עם מבנה מוכתב-מראש (modules, Guards, Pipes, Interceptors, Filters) במקום להשאיר את כל הארגון לבחירת המפתח.

**למה בחרנו בזה:** הוחלט ע"י ר"צ, כחלק מההחלטה על הפרדת קליינט/שרת (ר' עדכון בסעיף 4). NestJS היא הבחירה הנפוצה כש-Node.js צריך "framework מובנה" ברמה דומה למה שAngular נותן ל-frontend — מתאים לפרויקט שרוצה מבנה עקבי ונאכף (לא "עוד דרך אחת מיני רבות" כמו ב-Express הגולמי).

**יתרונות:**
- מבנה אחיד ונאכף (module/controller/service לכל משאב) — פחות החלטות ארגון "איך" בכל endpoint חדש.
- מנגנונים מובנים בדיוק למה שכבר היה צריך בגרסת ה-Route-Handler הישנה: Guards (=מה שהיה `proxy.ts`), Pipes (=ולידציה), Interceptors/Filters (=מעטפת תגובה אחידה) — לא היינו צריכים להמציא תחליף, NestJS כבר נותן את זה.
- אינטגרציה native ל-Swagger/OpenAPI (`@nestjs/swagger`, decorator-based) — פותר את החיסרון שצוין בסעיף 9 (Joi) לגבי תיעוד API ידני.
- תמיכה native ב-`@nestjs/testing` לבדיקות, ו-`@nestjs/throttler` ל-rate limiting (היה צריך ספרייה חיצונית קודם).

**חסרונות / סיכונים:**
- עקומת למידה תלולה יותר מ-Express הגולמי — מושגים כמו Modules/Providers/Decorators/DI צריך להכיר.
- תשתית נוספת מול המבנה הקודם (אפליקציה שנייה, deployment שני, CORS) — התיעוד המלא של ה-trade-off הזה ב-`ARCHITECTURE-SPINE.md`.
- Joi (לא `class-validator`, שהוא ברירת המחדל של NestJS) דורש Pipe מותאם-אישית (`JoiValidationPipe`) — לא "עובד מהקופסה" עם הכלים המובנים של Nest לולידציה/Swagger derivation; מתועד ב-`expertise-api-rest`.

**חלופות שנשקלו:** Express.js (גמיש יותר, פחות מובנה — זו הייתה ה"חלופה הקלאסית" שצוינה בסעיף 4 למעלה, ולבסוף לא נבחרה לטובת NestJS), Fastify (מהיר יותר מ-Express גולמי, אך גם הוא פחות מובנה מ-NestJS).

## 5. React Hook Form — ניהול טפסים בקלינט

**מה זה:** ספרייה שמנהלת את "מצב" הטפסים (מה המשתמש הקליד, אילו שדות לא תקינים, מה קורה כשלוחצים "שלח") בלי לגרום ל-React "לצייר מחדש" את המסך על כל הקשה במקלדת.

**למה זה מתאים לפרויקט:** יש כאן הרבה טפסים (רשומת איש קשר עם ~9 שדות, טופס רישום ציבורי, טפסי הודעות) — בדיוק המקרה שבשבילו הספרייה הזו נבנתה.

**יתרונות:**
- ביצועים טובים גם בטפסים גדולים (לא "מרנדר מחדש" את כל הטופס על כל הקשה).
- אינטגרציה נוחה עם ספריות ואלידציה (יש חבילת גישור ל-Joi: `@hookform/resolvers` — כך שאותה סכימת ואלידציה של Joi שתשמש בשרת יכולה (בהתאמה) לשמש גם בטופס בצד הקלינט לבדיקה מיידית, לפני השליחה לשרת).
- הספרייה הכי נפוצה כיום בעולם ה-React לטפסים.

**חסרונות / סיכונים:** עקומת למידה קלה (API מבוסס "hooks" — צריך להכיר את הרעיון של hooks ב-React).

**חלופות שנשקלו:** Formik (הייתה הפופולרית לפני RHF, כיום נחשבת פחות מתוחזקת/איטית יותר).

## 6. Mantine — ספריית רכיבי UI

**מה זה:** ספריית קומפוננטות מוכנות (טבלאות, טפסים, כפתורים, התראות, תפריטים) כדי לא לבנות כל רכיב ויזואלי מאפס.

**למה זה מתאים לפרויקט:** יש **תמיכה מובנית ומעולה ב-RTL** (עברית) — דרישה מפורשת במסמך (NFR-5), וזה לא כל ספריית UI תומכת בו בצורה חלקה. יש לה גם רכיבי טבלה/פילטרים מובנים שמתאימים לניהול רשימת אנשי קשר עם חיפוש וסינון (CM-7).

**יתרונות:**
- RTL "out of the box".
- מאות קומפוננטות מוכנות (כולל Forms hooks, Notifications, Modals) שיחסכו הרבה זמן פיתוח.
- תיעוד טוב, קהילה פעילה וגדלה.

**חסרונות / סיכונים:**
- פחות "ענקית" בהיקף השימוש מ-MUI (Material UI), כך שקצת פחות דוגמאות קוד קיימות באינטרנט (בפועל בדרך כלל לא מהווה בעיה).

**חלופות שנשקלו:** MUI (הכי נפוצה בעולם, אך תמיכת RTL דורשת הגדרה ידנית נוספת), Chakra UI (גם צריך הגדרה ל-RTL), Tailwind + Radix (גמיש מאוד אך דורש בניית עוד רכיבים בעצמכם — פחות מתאים ל-MVP מהיר).

## 7. Redux Toolkit — ניהול State גלובלי

**מה זה:** "State" הוא המידע שהאפליקציה זוכרת (למשל: מי המשתמש המחובר, אילו סינונים פעילים ברשימת אנשי הקשר). Redux Toolkit הוא כלי לנהל state ש**משותף** בין הרבה מסכים/קומפוננטות בבת אחת (בניגוד ל-state "מקומי" שרלוונטי לרכיב בודד).

**למה זה מתאים:** יש כאן צורך אמיתי ב-state משותף — למשל הרשאות המשתמש המחובר (רכז/מנהל-על/נציג גוף), שמשפיעות על מה שרואים במסכים שונים.

**יתרונות:**
- "הגרסה הרשמית והמומלצת" של Redux כיום — פותרת את רוב הבעיות שהיו ל-Redux הישן (הרבה "boilerplate", קוד חוזר).
- כלי חקירה (Redux DevTools) מעולה לדבאג — רואים כל שינוי ב-state עם "מכונת זמן" לחזור אחורה.
- מתאים לאפליקציות עם הרשאות/תפקידים מורכבים, כמו כאן.

**חסרונות / סיכונים:**
- לפרויקט MVP קטן יחסית זה עלול להיות "יותר מדי" — הרבה מהמידע (כמו רשימת אנשי קשר שמגיעה מהשרת) מנוהל היום לרוב בכלים ייעודיים ל"שליפת נתונים מהשרת" (כמו TanStack Query / RTK Query), ו-Redux "הרגיל" נשאר רק ל-state שבאמת גלובלי (כמו המשתמש המחובר). **נציע** בשלב הארכיטקטורה לשלב RTK Query (חלק מ-Redux Toolkit עצמו) גם לשליפת הנתונים מהשרת — כדי לא לכתוב קוד שליפה/קאשינג ידני בנפרד. זו לא סתירה לבחירה שלכם, אלא הרחבה טבעית שלה.

**חלופות שנשקלו:** Zustand (הרבה יותר "קליל", פופולרי מאוד לאחרונה, פחות boilerplate) — לא נבחר כי כבר יש החלטה על Redux Toolkit; React Context (מובנה ב-React, אך לא מיועד ל-state שמתעדכן הרבה, כמו רשימות/סינונים).

## 8. pg (node-postgres) + Prisma — גישה למסד הנתונים

**מה זה:**
- **PostgreSQL** ("Postgres") — מסד הנתונים היחסי עצמו (איפה שהמידע נשמר בפועל: אנשי קשר, גופים, משתמשים...).
- **pg** — ספריית Node.js "גולמית" לתקשורת ישירה עם Postgres (שולחים שאילתת SQL, מקבלים תוצאה).
- **Prisma** — "ORM" (Object-Relational Mapper): שכבה שמעליה, שמאפשרת לכתוב קוד JavaScript/TypeScript רגיל (`prisma.contact.findMany(...)`) במקום SQL גולמי, ומייצרת אוטומטית טיפוסי TypeScript מדויקים לפי מבנה הטבלאות.

**למה זה מתאים:** Postgres הוא מסד נתונים יחסי חזק, בטוח (ACID) ומתאים היטב לנתונים "טבלאיים" עם קשרים ברורים כמו כאן (איש קשר → שייך לגוף נתמך → שייך לתחום). Prisma הופך את הפיתוח למהיר ובטוח יותר.

**יתרונות:**
- Prisma מייצר Migration files (קבצים שמתעדים כל שינוי במבנה מסד הנתונים) אוטומטית — עונה ישירות לדרישה שלכם ל"סדר והקפדה על תיעוד" ולדרישת ה-Audit/היסטוריה (NFR-3, CM-3).
- Type-safety: אם משנים שדה בטבלה, הקוד שמשתמש בו "יישבר" מיידית בזמן כתיבה (ולא רק בזמן ריצה אצל משתמש) — פחות באגים.
- `pg` עדיין קיים "מתחת למכסה המנוע" (Prisma משתמש בו/דומה לו), כך שאין באמת התנגשות בין השניים — Prisma הוא השכבה שנשתמש בה בפועל ברוב הקוד; `pg` שימושי רק אם יידרש מקרה קצה של שאילתה מורכבת מאוד שקשה לבטא ב-Prisma.

**חסרונות / סיכונים:**
- שכבת הפשטה נוספת ללמוד (סינטקס Prisma משלו, קובץ `schema.prisma`).
- שאילתות SQL מורכבות מאוד-מאוד (נדיר ב-MVP) לפעמים קלות יותר לכתוב ב-SQL גולמי (`pg`) מאשר ב-Prisma.

**חלופות שנשקלו:** Drizzle ORM (חדש ופופולרי, "קרוב יותר" ל-SQL, אך פחות בשל/מתועד מ-Prisma נכון להיום), TypeORM (ותיק יותר, פחות "type-safe" בפועל מ-Prisma).

**עדכון (16/09/2026, מחקר לצורך `expertise-postgres-prisma` skill):** גרסת Prisma הנוכחית (7.x) **הסירה לגמרי** את ה-API הישן ליירוט שאילתות (`$use` middleware) שתוכנן במקור לצורך Audit Trail אוטומטי — כל קוד שהיה נכתב לפי דוגמאות ישנות פשוט לא יעבוד. ה-API הנוכחי הוא **Client Extensions** (`$extends`). זה תועד בפירוט (כולל קוד לדוגמה) ב-`.claude/skills/expertise-postgres-prisma/SKILL.md`, ויוטמע ב-Architecture Spine.

## 9. Joi — ואלידציה (בדיקת תקינות קלט)

**מה זה:** ספרייה להגדרת "כללים" למידע נכנס (למשל: "שדה email חייב להיות בפורמט אימייל תקין", "שדה phone הוא מחרוזת חובה") ולבדוק לפיהם קלט שמגיע מהמשתמש (בטופס) או מבקשת API, **לפני** שהוא נכנס למסד הנתונים.

**למה זה מתאים:** דרישה מפורשת במסמך (CM-5 — בקרת תקינות לדוא"ל; REG-8 — הגנה מפני spam בטופס הפומבי). Joi היא ספריית ואלידציה ותיקה, יציבה ומוכרת מאוד בעולם Node.js.

**יתרונות:**
- API ברור וקריא, המון תיעוד ודוגמאות (קיימת שנים רבות, נחשבת "בטוחה" ובדוקה).
- לא תלויה ב-TypeScript — עובדת מצוין גם בפרויקט JavaScript רגיל.

**חסרונות / סיכונים (חשוב לדעת מראש):**
- **בניגוד ל-Zod (החלופה המובילה כיום), Joi לא "מייצרת" טיפוסי TypeScript אוטומטית מתוך סכימת הואלידציה.** בפועל זה אומר: אם נבחר ב-TypeScript לפרויקט (⚠️ מחכה להחלטה שלכם — ראו השאלות בהודעה), נצטרך לכתוב את טיפוס הנתונים **פעם אחת נפרדת** (interface/type) **וגם** את סכימת ה-Joi בנפרד — במקום שTypeScript "יבין" אוטומטית מה השדות לפי הסכימה כמו שקורה עם Zod. זה לא חוסם שום דבר, רק עבודה כפולה קטנה בכל טופס/API.
- זה גם משפיע ישירות על ה-Swagger/OpenAPI (תיעוד ה-API): עם Zod יש כלים שמייצרים את מסמך ה-OpenAPI **אוטומטית** מתוך סכימות הואלידציה. עם Joi, ניצור את תיעוד ה-Swagger בנפרד (ראו שאלה בהמשך ההודעה).

**חלופות שנשקלו:** Zod (הכי נפוץ כיום בפרויקטי TypeScript חדשים, בזכות ה"אינטגרציה" עם טיפוסים), Yup (דומה ל-Joi, פחות נפוץ כיום).

## 12. סגנון ה-API: REST

**מה זה:** REST הוא סט מוסכמות מקובל לעיצוב API — איך בונים כתובות (URL) ואיך משתמשים בפעולות HTTP (Methods), כך שכל מי שמכיר REST יודע לצפות מראש איך ה-API מתנהג, בלי לקרוא תיעוד לכל endpoint בנפרד.

**למה נבחר:** בהנחייתכן המפורשת לעבוד לפי כללי REST. זו גם ברירת המחדל המתבקשת עם Swagger/OpenAPI (שנבחר למעלה) — הפורמט של OpenAPI בעצמו בנוי סביב resources ו-HTTP methods, בדיוק כמו REST.

**העקרונות שנעבוד לפיהם (יעוגנו רשמית וביתר פירוט בשלב הארכיטקטורה):**
- **Resources ולא פעולות בכתובת** — למשל `/api/contacts` ולא `/api/getContacts` או `/api/contact-list`.
- **שימוש נכון בפעולות HTTP** לפי המשמעות המקובלת:
  - `GET /api/contacts` — שליפת רשימת אנשי קשר (עם query params לחיפוש/סינון, כנדרש ב-CM-7: `?bodyId=...&status=...`).
  - `GET /api/contacts/:id` — שליפת איש קשר בודד.
  - `POST /api/contacts` — יצירת איש קשר חדש.
  - `PATCH /api/contacts/:id` — עדכון חלקי (למשל רק סטטוס ל"לא פעיל", לפי CM-3).
  - `DELETE` — **לא ינוקד באמת** על רשומות אנשי קשר (לפי CM-3 אין מחיקה אמיתית, רק סימון "לא פעיל") — ייתכן שנחשוף `DELETE` כ"מחיקה רכה" (soft delete) שקוראת בפועל ל-`PATCH`, נחליט זאת רשמית בארכיטקטורה.
- **קודי סטטוס HTTP משמעותיים** — `200`/`201` להצלחה, `400` לקלט לא תקין (נכשל ב-Joi), `404` לרשומה שלא נמצאה, `401`/`403` להרשאות (רלוונטי ל-GR-1/GR-2), ולא להחזיר תמיד `200` עם שדה "success: false" בגוף התשובה (טעות נפוצה שפוגעת בעקביות).
- **תשובות עקביות** — מבנה JSON אחיד לשגיאות ולהצלחות, כך שהקלינט (React) יכול לטפל בהן בצורה גנרית.
- **גרסאות (Versioning)** — נדון בשלב הארכיטקטורה אם צריך `/api/v1/...` כבר מה-MVP או רק כשיהיה צורך אמיתי בשינוי לא-תואם-לאחור.

**יתרונות:**
- מוסכמה מוכרת מאוד — כל מפתח שיצטרף לפרויקט "כבר יודע" איך ה-API מתנהג.
- משתלב טבעי עם Swagger/OpenAPI ועם `next-swagger-doc`/`swagger-jsdoc` שנבחרו.

**חסרונות / סיכונים:**
- לפעמים "נטו-REST" נהיה מסורבל לפעולות שהן לא CRUD טהור (למשל "אישור בקשת רישום" ב-REG-5/REG-6 — פעולה עסקית, לא רק עדכון שדה). נפתור זאת בדרך כלל עם endpoint ממוקד-פעולה בתוך ה-resource, למשל `POST /api/registration-requests/:id/approve` — עדיין REST-י, רק פחות "טהור" מבחינה תיאורטית. נתעד כל מקרה כזה בפועל כשנגיע אליו.

**חלופות שנשקלו:** GraphQL (גמיש יותר לשאילתות מורכבות בצד קלינט, אך overhead משמעותי להקמה ל-MVP ולא התבקש) — לא נבחר, בהתאם להנחייתכן המפורשת ל-REST.

**עדכון (16/09/2026, מחקר לצורך `expertise-api-rest` skill):** הכלי המקורי שתוכנן לתיעוד Swagger — `next-swagger-doc` — **לא עודכן מעל שנה**, בעוד שקיים כלי מתחרה פעיל ומתוחזק, בנוי ספציפית ל-Next.js App Router: **`next-openapi-gen`**. שווה לשקול מעבר לפני שמתחילים לכתוב את שכבת ה-API בפועל. פירוט מלא ב-`.claude/skills/expertise-api-rest/SKILL.md`.

**עדכון (24/09/2026, בעקבות ההחלטה על NestJS — ר' סעיף 4A):** ההערה הקודמת (`next-openapi-gen`) **התייתרה** — היא הייתה רלוונטית רק כשה-API היה Next.js Route Handlers. עכשיו שה-API כולו עבר ל-`apps/api` (NestJS), תיעוד ה-Swagger נעשה עם **`@nestjs/swagger`** — כלי native ל-framework, מבוסס decorators (`@ApiOperation`, `@ApiResponse`), לא JSDoc. עקרונות ה-REST/URL/HTTP-method/status-code בסעיף הזה **לא השתנו** — רק המימוש הטכני של התיעוד. פירוט: `expertise-api-rest`.
